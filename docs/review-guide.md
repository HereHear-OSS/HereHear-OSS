# 코드리뷰 가이드

HereHear-OSS 팀의 PR 리뷰 기준입니다. 목표는 **버그를 막고, 서로 배우고, 코드를 읽기 쉽게 유지하는 것**입니다.

## 1. 리뷰 태그

모든 코멘트는 아래 태그 중 하나로 시작합니다.

| 태그 | 의미 | 병합 전 처리 |
| --- | --- | --- |
| `[MUST]` | 반드시 수정해야 함 (버그, 보안, 데이터 오류, 팀 규칙 위반, 빌드 실패) | **필수 해결** |
| `[SHOULD]` | 수정을 권장함 (가독성, 중복, 네이밍, 성능, 테스트 보강) | 반영하거나, 안 하는 이유를 답글로 남김 |

> 칭찬이나 질문은 태그 없이 `👍`, `❓` 로 가볍게 남겨도 됩니다.

### [MUST] 판단 기준
- 동작하지 않거나 기능 요구사항(등록 → 발견 → 재생 → 저장)을 깨뜨리는 경우
- 반경(2km) 판정, 중복 등록 제한 등 **핵심 정책 위반**
- Supabase 키·토큰 등 비밀 값 노출, 권한(RLS) 누락
- `npm run lint` / `npm run build` 실패
- Conventional Commits, 브랜치 규칙 등 CONTRIBUTING 위반

### [SHOULD] 판단 기준
- 중복 코드, 너무 긴 함수/컴포넌트
- 의미가 불분명한 변수·함수 이름
- 예외 처리·로딩/에러 UI 보강
- 테스트(Playwright E2E) 추가 제안
- 주석·문서 보강

## 2. 코멘트 작성법

**형식:** `[태그] 문제 → 이유 → 제안`

```text
[MUST] src/... 에서 Supabase anon 키가 코드에 하드코딩되어 있어요.
저장소가 public이라 키가 그대로 노출됩니다. .env로 옮기고
import.meta.env.VITE_SUPABASE_ANON_KEY 로 읽도록 바꿔 주세요.

[SHOULD] 거리 계산 로직이 두 컴포넌트에 반복돼요.
utils/distance.js 로 분리하면 반경 2km 판정을 한 곳에서 관리할 수 있습니다.

[SHOULD] 변수명 `d`는 의미를 알기 어려워요. `distanceMeters` 처럼 단위까지 드러내면 어떨까요?

👍 바텀시트 열림/닫힘 상태를 하나의 state로 정리한 부분이 깔끔해요.
```

## 3. 리뷰 체크리스트

**기능**
- [ ] PR 설명의 "테스트 방법"대로 직접 실행해 봤는가
- [ ] 연결된 Issue의 요구사항을 모두 충족하는가
- [ ] 반경 밖·빈 데이터·권한 없음 같은 예외 상황을 처리하는가

**코드 품질**
- [ ] 이름이 명확하고 중복이 없는가
- [ ] 컴포넌트·함수가 한 가지 역할만 하는가
- [ ] 불필요한 `console.log`, 주석 처리된 코드가 없는가

**보안 · 설정**
- [ ] `.env`, 키, 토큰이 커밋에 포함되지 않았는가
- [ ] Supabase 정책(RLS)이나 스키마 변경이 있다면 `/supabase`에 반영되었는가

**규칙**
- [ ] 브랜치 이름, 커밋 메시지, PR 제목이 규칙을 따르는가
- [ ] PR 크기가 리뷰 가능한 수준인가

## 4. 리뷰 제출 방법

1. PR의 **Files changed** 탭에서 줄 옆 `+` 로 줄 단위 코멘트를 남깁니다. (`Start a review`)
2. 전체 의견을 **Review changes** 에서 요약하고 결과를 선택합니다.
   - **Approve**: `[MUST]`가 없고 병합해도 좋음
   - **Request changes**: `[MUST]`가 있어 수정이 필요함
   - **Comment**: 질문·의견만 남김
3. 수정 후 재요청이 오면 해결 여부를 확인하고 Resolve 합니다.

## 5. 태도

- 사람이 아니라 **코드**에 대해 이야기합니다.
- "왜"를 함께 설명하고, 가능하면 대안을 제시합니다.
- 작성자는 방어적으로 받아들이지 않고, 동의하지 않으면 근거를 들어 답글로 논의합니다.
