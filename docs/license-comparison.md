# 오픈소스 라이선스 비교와 선택 기준

HereHear 저장소에 어떤 라이선스를 적용할지 정하기 위해 대표적인 오픈소스 라이선스 4종을 비교하고 선택 기준을 정리했습니다.
결론부터 말하면 HereHear는 **MIT 라이선스**를 선택했습니다.

> 이 문서는 학습용 정리이며 법률 자문이 아닙니다. 실제 배포 전에는 각 라이선스 원문을 확인하세요.

## 1. 라이선스 4종 한눈에 비교

| 구분 | MIT | Apache-2.0 | GPL-3.0 | MPL-2.0 |
| --- | --- | --- | --- | --- |
| 분류 | 허용형 (permissive) | 허용형 (permissive) | 강한 카피레프트 | 약한 카피레프트 (파일 단위) |
| 핵심 의무 | 저작권·라이선스 고지 유지 | 고지 유지, 변경 사항 표시, NOTICE 유지 | 배포할 때 파생물 전체를 GPL-3.0으로 소스 공개 | 수정한 MPL 파일의 소스 공개 |
| 특허 | 명시적 조항 없음 | 명시적 특허 허여, 특허 소송 시 권리 종료 | 명시적 특허 허여 | 명시적 특허 허여 |

| 주의할 점 | 특허 문제를 직접 다루지 않음 | 문서가 길고 고지 의무가 많음. GPL-2.0-only와는 호환되지 않음 | 상용·비공개 제품에 쓰기 어려움 | 파일 단위 규칙이 다소 복잡함 |

## 2. 선택 기준

1. **파생물 공개 의무**: 이 프로젝트를 가져다 쓴 사람이 자기 코드를 공개해야 하는가
2. **특허 조항**: 기여자와 사용자 사이의 특허 분쟁 위험을 명시적으로 다루는가
3. **의존성 라이선스와의 호환**: 사용 중인 라이브러리의 라이선스와 충돌하지 않는가
4. **사용 용이성**: 기업과 개인이 부담 없이 가져다 쓸 수 있는가
5. **생태계 관행**: 같은 생태계(npm, React)에서 흔히 쓰는 라이선스인가
6. **프로젝트 목표**: 학습과 확산이 목적인지, 개방성 유지나 상용화가 목적인지

## 3. HereHear의 선택: MIT

| 기준 | HereHear 상황 | 판단 |
| --- | --- | --- |
| 파생물 공개 의무 | 학기 프로젝트이며 누구나 보고 배울 수 있게 공개하는 것이 목적 | 공개를 강제할 이유가 없어 허용형이 적합 |
| 특허 조항 | 특허 출원 계획이나 기업 기여자가 없음 | MIT로 충분. 기업 협업이 생기면 Apache-2.0 재검토 |
| 의존성 호환 | 직접 의존성에 GPL 계열이 없음 (React, supabase-js 등은 MIT, Leaflet은 BSD-2-Clause) | MIT와 충돌 없음. 4절의 react-leaflet 참고 |
| 사용 용이성 | 팀원과 외부 기여자 모두 부담 없이 쓰게 하고 싶음 | 짧고 단순한 MIT가 유리 |
| 생태계 관행 | npm·React 생태계에서 MIT가 흔함 | 관행과 일치 |
| 프로젝트 목표 | 등록 → 발견 → 재생 → 저장 MVP 완성과 학습 | 단순함이 목표에 맞음 |

## 4. 주의할 점

- **의존성 라이선스**: react-leaflet 4.x는 윤리 조항이 있는 Hippocratic License 2.1로 배포됩니다. MIT처럼 단순한 허용형이 아니므로 앱을 배포하기 전에 조건을 읽어 보세요. 이 저장소의 코드를 MIT로 공개하는 것과는 별개의 문제입니다. 전체 의존성은 `npx license-checker --production --summary`로 점검할 수 있습니다.
- **프론트엔드 번들**: 웹 앱의 프론트엔드 코드는 사용자 브라우저로 전달(배포)됩니다. GPL 계열 라이브러리를 새로 추가할 때는 공개 의무가 생길 수 있으니 의존성을 추가하기 전에 라이선스를 확인합니다.
- **코드 외 자산**: `public/audio`의 음원, 이미지, 폰트는 코드 라이선스(MIT)와 별개입니다. 출처와 이용 조건을 기록해 둡니다.
- **라이선스 변경**: 공개한 뒤에 바꾸려면 기여자 동의가 필요할 수 있으므로 초기에 신중히 정합니다.
