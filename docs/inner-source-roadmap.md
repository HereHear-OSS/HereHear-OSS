# Inner Source 도입 로드맵

## 1. Inner Source란

오픈소스의 협업 방식(공개된 코드, 이슈와 PR 기반 기여, 문서화, 코드리뷰)을 조직 안에서만 적용하는 방식입니다.
코드는 조직 구성원에게 공개하되 외부에는 공개하지 않습니다. 팀 간 사일로를 줄이고 재사용과 협업을 늘리는 것이 목표입니다.

HereHear 저장소는 README, LICENSE, CONTRIBUTING, CODE_OF_CONDUCT를 갖춘 OSS 기본 구조를 이미 만들었으므로, 조직에서 Inner Source를 시작할 때 **파일럿 후보이자 템플릿**으로 쓸 수 있습니다.

## 2. 목표와 원칙

**목표**

- 다른 팀이 기여할 수 있는 저장소를 늘린다
- 중복 개발을 줄이고 재사용을 높인다
- 기여 경험을 쌓아 협업 문화를 만든다

**원칙**

- 기본은 조직 내부 공개이며 모든 변경은 PR과 리뷰를 거친다
- 기여자를 돕는 신뢰할 수 있는 커미터(Trusted Committer) 역할을 둔다
- 문서가 곧 지원 채널이다 (README, CONTRIBUTING 중심)
- 작게 시작하고 지표로 확인하며 넓힌다

## 3. 단계별 로드맵

| 단계 | 기간 | 목표 | 완료 기준 |
| --- | --- | --- | --- |
| 0. 준비 | 1~2개월 | 방향 합의와 기반 정비 | 후원자 확정, 정책 초안, 파일럿 후보 선정 |
| 1. 파일럿 | 3개월 | 1~2개 프로젝트로 방식 검증 | 타 팀 기여 PR 첫 병합, 지표 수집 시작 |
| 2. 확산 | 6개월 | 참여 프로젝트와 기여자 확대 | 참여 프로젝트 5개 이상(예시 목표), 프로젝트 목록 포털 운영 |
| 3. 정착 | 이후 | 제도화와 지속 개선 | 지표 정기 점검, 평가·보상 연계 |

### 단계 0: 준비 (1~2개월)

- 경영진과 팀장 중 후원자를 확보하고 목표를 합의한다
- 현황을 진단한다: 저장소 분산, 중복 개발, 문서화 수준, 보안과 라이선스 정책
- 기본 정책 초안을 만든다: 공개 범위(조직 내부), 코드 소유권, 기여 절차, 비밀 값 커밋 금지
- 표준 문서 템플릿을 준비한다: README, CONTRIBUTING, CODE_OF_CONDUCT, LICENSE(내부 사용 조건), 이슈·PR 템플릿. HereHear 구조를 기반으로 한다
- 파일럿 후보 기준을 정한다: 다른 팀이 쓸 가치, 담당 팀의 의지, 위험이 낮은 프로젝트

### 단계 1: 파일럿 (3개월)

- 1~2개 프로젝트(HereHear 포함)에 OSS 기본 구조를 적용한다
- Trusted Committer를 지정하고 리뷰 응답 목표를 정한다 (예: 24시간, HereHear CONTRIBUTING의 규칙)
- CI를 구성해 외부 기여 PR이 자동으로 검증되게 한다
- `good first issue` 라벨을 붙이고 기여 안내 세션을 연다
- 첫 타 팀 기여를 받고 회고한다
- 지표 수집을 시작한다

### 단계 2: 확산 (6개월)

- 내부 포털이나 검색·태그 규칙으로 프로젝트를 쉽게 찾게 하고, 프로젝트를 소개하는 자리를 마련한다
- 템플릿 저장소와 온보딩 문서로 새 프로젝트를 쉽게 등록하게 한다
- 질문과 지원 채널(GitHub Discussions, 사내 메신저)을 정비한다
- 프로젝트별 성숙도와 거버넌스 단계를 표기해 기여자의 혼란을 줄인다
- 기여자를 공개적으로 인정하고 평가에 반영한다
- 새 Trusted Committer를 키우고 역할을 순환한다

### 단계 3: 정착 (이후)

- 지표를 분기마다 점검하고 개선한다
- 성숙도 모델로 프로젝트를 평가한다
- 운영 그룹이나 검토 위원회가 정책, 지표, 교육을 맡는다
- 필요하면 일부 프로젝트를 외부 오픈소스로 전환할 준비를 한다

## 4. 역할

| 역할 | 하는 일 |
| --- | --- |
| 후원자 | 정책과 자원을 지원하고 장애물을 치운다 |
| 프로젝트 오너 (호스트 팀) | 로드맵과 이슈를 관리하고 기여 가이드를 유지한다 |
| Trusted Committer | 타 팀 PR을 리뷰하고 기여자를 멘토링하며 코드 품질을 지킨다 |
| 기여자 | 이슈를 확인한 뒤 가이드에 맞게 PR을 올린다 |
| 운영 그룹 | 정책, 지표, 교육을 관리한다 |

## 5. 성공 지표 (Goal-Question-Metric)

| 목표 | 질문 | 지표 |
| --- | --- | --- |
| 협업 확대 | 다른 팀이 얼마나 기여하는가 | 타 팀 PR 수와 비율 |
| 기여 경험 | 기여가 얼마나 빨리 처리되는가 | 첫 리뷰까지 시간, PR 병합 리드타임 |
| 지속성 | 새 기여자가 계속 참여하는가 | 신규 기여자 수, 재기여 비율, 기여자에서 커미터로 전환되는 비율 |
| 재사용 | 프로젝트가 다른 곳에서 쓰이는가 | 사용 횟수, 참여 저장소 수 |
| 전달 성능 | 협업이 개발 속도에 영향을 주는가 | DORA 4지표 (배포 빈도, 변경 리드타임, 변경 실패율, 복구 시간) |
| 만족도 | 참여자가 만족하는가 | 정기 설문 |

## 6. 위험과 대응

| 위험 | 대응 |
| --- | --- |
| Trusted Committer가 없어 리뷰가 늦어지고 기여자가 떠남 | 역할을 지정하고 순환하며 업무 시간을 확보한다 |
| 문서가 부족해 진입장벽이 높음 | 템플릿과 CONTRIBUTING을 필수로 한다 |
| 기여할 동기가 부족함 | 평가에 반영하고 공개적으로 인정한다 |
| 비밀 값이나 개인정보 노출 | 비밀 값 커밋 금지, 시크릿 스캔, 접근 권한 관리 |
| 프로젝트마다 운영 단계가 달라 혼란 | 거버넌스 단계를 표기한다 |
| 리뷰 병목 | 리뷰 응답 목표를 두고 린트·CI로 스타일 검토를 자동화해 리뷰는 설계에 집중한다 |

## 7. HereHear 파일럿 적용 예

| 항목 | 현재 | 다음 단계 |
| --- | --- | --- |
| 문서 | README, LICENSE, CONTRIBUTING, CODE_OF_CONDUCT 완비 | 조직 표준 템플릿으로 추출 |
| 리뷰 규칙 | PR당 최소 1명 승인, 24시간 내 1차 리뷰 목표 | Trusted Committer 지정 |
| 자동화 | GitHub Actions CI, 주간 DORA 리포트 | 타 팀 PR도 같은 CI로 검증 |
| 지표 | 주간 DORA 리포트 | 타 팀 PR 비율, 리뷰 시간 추가 |
| 진입장벽 | 이슈 기반 작업 | `good first issue` 라벨과 온보딩 안내 |
